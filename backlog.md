# Backlog

Atomic tasks, not a priority-ordered roadmap. Each entry is a problem or gap
someone (or an agent) could pick up and finish in one sitting without asking
"what does this mean?" first. Product ideas live in `docs/future-ideas.md`;
this file is defects, gaps, and known ceilings in what already exists.

Sections describe what *kind* of change an entry is, not how urgent it is —
pick whichever section matches the task at hand, there's no priority order
within or across them:

- **Features** — capability that doesn't exist today.
- **Bugs** — existing functionality doesn't do what it's supposed to.
- **Improvements** — same behavior, better/cleaner/faster/safer underneath.

Rules for keeping this file real:

- Every entry must be actionable right now. If it's not, it doesn't belong here.
- When an item is fixed, delete it. Don't check it off and leave it, don't move it to a "done" or "changelog" list — git history is the changelog.
- When a decision is made and closed with no remaining follow-up work, delete it too. Don't keep a "Decided / won't fix" graveyard.
- No dates, no "as of this session", no "swept on", no references to when something was added or by whom. This file describes the current state of the codebase, not its history.
- If a fix is genuinely speculative (no concrete trigger yet), say so plainly and give the trigger condition — don't leave vague "might be nice" entries.
- Prefer deleting or rewriting a stale entry over leaving it half-true when the code has moved past it. New entries follow this same file's own rules — keep it that way.

## Features

- [ ] **Widget resize** — today `w`/`h` are a first-launch hint only; there's no interactive way to change a widget's grid size after it's placed. The drag grip was deliberately narrowed to the header's top-right corner (`WidgetHeader` in `src/wigl/widget.tsx`, `data-drag-handle`) specifically so a resize handle has an uncontested spot to live — the natural pairing is a `data-resize-handle` grip at the bottom-right corner of `<Widget>`'s root, driving `reportGrid`'s `w`/`h` through the same `reflow`/`settle` machinery `src/wigl/Desktop.tsx` already uses for drag. Trigger: someone wants to actually resize a widget, not just reposition it.
- [ ] **Multiple instances of one widget type** — today a widget is exactly one folder = one id = one instance, so two clocks on different timezones is impossible. `<Widget w h col row>` itself doesn't care about identity; the gap is discovery (folder name *is* the id) and storage (each instance needs its own key, not a shared one). A plugin's `package.json` (`wigl` key) is the obvious place for this to land — a plugin declaring it's instantiable, with the user's chosen instances and per-instance overrides stored like any other layout state. Trigger: a concrete want for two instances of one widget type.
- [ ] **Escape cancels a drag** — deliberate gap, not an oversight: `screen-*` windows are `alwaysOnBottom` and rarely become key, so a `keydown` listener isn't a reliable place to catch Escape. Trigger: revisit if/when there's a reason one of these windows does become key (e.g. a command palette), since that would give you a reliable focus target to hang the listener off.
- [ ] **Smoother iteration when editing a widget** — `bun run plugin:install` writes to the app-data dir, and nothing tells a running app to re-read it, so it's build → install → relaunch every time. `loadPlugins()` is already idempotent, so a watch mode plus a "reload plugins" global action would cut the loop to one keystroke. Trigger: someone finds the build→install→relaunch loop annoying enough to spend an afternoon on it.
- [ ] **A plugin is not sandboxed** — `src/wigl/plugins/registry.ts` controls which modules a plugin can import, which is real (it's how a withheld permission actually withholds something), but plugin code runs in the host's JS realm with `csp: null`, so `window.__TAURI_INTERNALS__` is reachable directly by anything that wants it. Today that's acceptable — plugins are hand-installed from a local folder by the person running the app. It stops being acceptable the moment plugins are installed from a URL or a registry. Fix shape when that trigger arrives: run each plugin in a worker or sandboxed iframe with the host API exposed over a message port, or adopt Tauri's isolation pattern; both are large enough that they want their own design pass, and both are much cheaper to adopt *before* a plugin ecosystem exists than after.
- [ ] **Plugin storage keys aren't namespaced** — `useStorage`/`useQuery` write into one shared kv table keyed by whatever string the caller passes, so two plugins picking the same key silently share (and clobber) state, and nothing scopes a key to the plugin that owns it. Harmless with today's hand-installed plugins, a real bug the first time two independently-authored ones collide. Fix shape: have the registry hand each plugin a `useStorage` pre-bound to a `<plugin-id>:` prefix rather than the raw hook — the registry already builds a per-plugin view of `@/wigl/hooks`, so there's a natural place for it with no new concept.
- [ ] **The plugin registry chunk carries all of `lucide-react`** — `registry.ts` holds a live reference to every module it can serve, so the whole icon set lands in one chunk (~618kb unminified). It's dynamically imported and therefore only paid when at least one plugin is actually installed, which is why this isn't urgent. Trigger: someone notices first-plugin-load latency. Fix shape: serve icons through a lazy per-icon lookup instead of a namespace import, which also removes the "host must ship every icon a plugin might want" coupling.

## Bugs

- [ ] **Cross-monitor drag col/row offset on screens of different sizes** — reported symptom: dragging a widget from a smaller screen to a bigger one (or vice versa) lands it at an unexpected position. `GridItem`/`SavedPositions`/the drag message payloads were renamed `x`/`y` → `col`/`row` for a clear API, but the underlying fix isn't implemented yet — a static read of `onPointerMove`'s foreign-monitor branch in [Desktop.tsx](src/wigl/Desktop.tsx) (target `col`/`row` come from `pxToCol`/`pxToRow` against the *target* monitor's own `colsForWidth`, which already looks size-aware) didn't turn up an obvious cause, so the repro needs pinning down first. Likeliest suspects to check while reproducing: `d.offX`/`d.offY` (captured once at drag-start from the source monitor, reused verbatim once the cursor is over a different monitor) and `TILING.padding.top` (a flat 48px menu-bar clearance applied to every monitor, including ones without a menu bar). Fix shape once confirmed: a small helper that recomputes a relative `col`/`row` for monitor B from monitor A's `col`/`row` and each monitor's own column/row capacity, instead of reusing a raw pixel offset across monitors. Re-audited statically this pass: `d.offX`/`d.offY`, `TILING.padding.top`, and the `cols`/clamp math in the foreign-monitor branch of `onPointerMove` all check out as monitor-size-aware on paper (cell size is a global constant, not monitor-dependent, so no resize-driven drift either). The remaining untested lead is `monitors.current` normalizing `availableMonitors()` rects by each monitor's own `scaleFactor` while `e.screenX`/`e.screenY` are taken as-is — if a platform ever reports `screenX`/`screenY` in a scale that isn't uniform across displays of different DPI (behavior is OS/compositor-dependent), that mismatch would reproduce exactly this symptom. Needs a live multi-DPI multi-monitor rig to confirm; still not reproduced.
- [ ] **Windowed-mode interactive flows unverified end-to-end** — the Wayland/GNOME windowed flow (`docs/architecture.md`) has been confirmed to build and launch cleanly on a real Linux/GNOME machine (correct mode detection, clean log, `tauri://localhost` page load), and click-through was tried live and reverted, confirmed not worth keeping without positioning/stacking control (see `docs/architecture.md`) — but drag/drop within the single window, `useStorage` read/write, the per-widget error boundary actually catching a crash, and the repos widget's Linux-specific shell paths (`wigl-widgets/repos/commands.ts`'s `xdg-open`/VS Code CLI/GitHub Desktop community-fork branches) still haven't been exercised interactively — no input-synthesis tool was available to script clicks/drags in the environment this was checked from. Trigger: someone with hands on a real Linux/GNOME machine spends 15–20 minutes actually dragging widgets, toggling repos-widget settings, and clicking its action buttons.
- [ ] **(Low priority) Drag ghosting/residue in windowed mode (GNOME/Wayland)** — dragging a widget leaves a visual trail of its previous position(s) that doesn't clear until something forces a repaint. Not reproduced interactively in this pass (no input-synthesis tool available in the environment this was investigated from — no `ydotool`/`wtype`/`xdotool` installed, and synthesizing real mouse events via `/dev/uinput` on someone's live session is too invasive to do unprompted), so this is a hypothesis, not a confirmed root cause. Likeliest mechanism: `.wigl-widget` (`src/App.css`) is `will-change: transform` and gets its position written via a raw `el.style.transform` on every `pointermove` during a drag ([Desktop.tsx](src/wigl/Desktop.tsx)'s `onPointerMove`) — a GPU-layer-promoted transform animated at pointer rate is exactly the pattern that trips known WebKitGTK compositor damage-region bugs, and `lib.rs`'s `run()` already sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` by default on Linux (worked around a *different* bug — blank windows on some GPU/external-display combos — see `docs/debugging.md`), which forces a fallback rendering path that's a plausible place for a *new* repaint/damage bug to show up. Cheap things to try first, in order: (1) A/B test with DMA-BUF re-enabled — launch with `WEBKIT_DISABLE_DMABUF_RENDERER= bun run qa:app` (empty value overrides the default) and see if ghosting disappears; if so the two workarounds are in tension and need a driver-specific condition instead of a blanket default. (2) `WEBKIT_DISABLE_COMPOSITING_MODE=1` (already noted in `docs/debugging.md` as a blunter fallback) as a second data point. (3) If neither clears it, it's likely a Mesa/driver-specific WebKitGTK compositor bug rather than anything in this app's CSS/drag code — check `journalctl --user -b 0 | grep -i webkit` for driver-level messages while reproducing. Trigger to pick this up: someone with a GNOME/Wayland machine and a spare 20 minutes to actually drag a widget and try the two env-var A/B tests above.
- [ ] **(Very low priority) GNOME-native overlay flow via a Shell extension** — Wayland/GNOME sessions currently get the windowed flow (`docs/architecture.md`) instead of the real desktop-overlay one, because stock GNOME Wayland refuses a client absolute positioning and always-below/always-on-top stacking (click-through alone isn't the gap — that part actually works over Wayland, it just isn't useful without one of those two to keep the window out of the way; see `docs/architecture.md`). A GNOME Shell extension ([desktop-widgets](https://github.com/NiffirgkcaJ/desktop-widgets)-style) could plausibly grant enough positioning/stacking control to run the real per-monitor overlay flow under GNOME too. Not worth pursuing casually: it's an extra install step for the user (extensions aren't bundled with the app), version-fragile against GNOME Shell updates in a way the current windowed flow isn't, and would need real QA on the positioning/stacking contract before it's safe to switch GNOME users onto it by default. Trigger: someone's actually bothered enough by the windowed flow's remaining UX gap (window doesn't stay pinned below/above other apps, doesn't span monitors) to want to try it.

## Improvements

- [ ] **`useQuery`'s SQL cache never evicts** — `src/wigl/storage/useQuery.ts`'s `useSql: true` path writes `query_<key>` rows into the shared kv table but nothing ever deletes one, so a renamed or retired query key leaves a dead row behind forever (harmless, just clutter). Trigger: enough renamed/retired query keys to notice in the DB. Fix shape: none needed until then — a manual `DELETE FROM kv WHERE key LIKE 'query_%'` sweep is enough when it does.
