# Backlog

Atomic tasks, not a priority-ordered roadmap. Each entry is a problem or gap
someone (or an agent) could pick up and finish in one sitting without asking
"what does this mean?" first. Product ideas live in `docs/future-ideas.md`;
this file is defects, gaps, and known ceilings in what already exists.

Two sections, by size of change, not urgency — there's no priority order
within or across them:

- **Bugs** — existing functionality doesn't do what it's supposed to, or a
  targeted, self-contained fix/tweak to something that already works.
- **Features** — a capability that doesn't exist today, big enough that
  building it changes the current flow rather than just patching it.

Rules for keeping this file real:

- Every entry must be actionable right now. If it's not, it doesn't belong here.
- When an item is fixed, delete it. Don't check it off and leave it, don't move it to a "done" or "changelog" list — git history is the changelog.
- When a decision is made and closed with no remaining follow-up work, delete it too. Don't keep a "Decided / won't fix" graveyard.
- No dates, no "as of this session", no "swept on", no references to when something was added or by whom. This file describes the current state of the codebase, not its history.
- If a fix is genuinely speculative (no concrete trigger yet), say so plainly and give the trigger condition — don't leave vague "might be nice" entries.
- Prefer deleting or rewriting a stale entry over leaving it half-true when the code has moved past it. New entries follow this same file's own rules — keep it that way.

## Bugs

- [ ] **LocalCode: `/think off` doesn't actually stop the model thinking** — `Composer.tsx`'s `/think off` clears the request's `variant`, which means *no reasoning-effort override*, not *thinking disabled*; a thinking-capable Ollama model reasons by default regardless. Ollama's own API has the real switch (`"think": false` on `/api/chat`); unconfirmed whether opencode's generic `openai-compatible` provider forwards anything that reaches it. To settle it: put a reverse proxy between opencode and Ollama, send the same seeded prompt through `POST /session/{id}/message` three ways — no `variant`, `variant: "high"`, and an `off` variant declared as `{ think: false }` in `opencode.jsonc` — and diff the request bodies the proxy captures. Whichever key survives is what `wigl-widgets/LocalCode/opencodeConfig.ts`'s `syncOllamaModels()` should write for the off/low/high variants; if nothing survives, delete `/think` from `wigl-widgets/LocalCode/commands.ts` and say so in its `AGENTS.md`.
- [ ] **LocalCode: opencode's `build` agent can hang indefinitely against Ollama** — reproduced live: the same prompt/model/options that answers correctly in ~2s through plain Ollama never returns through opencode's `POST /session/{id}/message` with `agent: "build"` (the widget's default — no `agent` also resolves to this), even after 90s, with no `session.idle`/`session.error` ever firing. Not model size or prompt content (both a 0.8B and 9B model reproduce it; both an open-ended and closed-form prompt do too) — isolates to something in the `build` agent's tool schema / opencode's Ollama provider path. Two unconfirmed candidates: `options.num_predict` not actually reaching Ollama through opencode's request construction, or a tool-call loop that doesn't terminate against this provider. Confirming either needs a local reverse proxy between opencode and Ollama to capture the real outgoing request bodies — not fixable by reading wigl's own code. User-facing exposure today is bounded (the composer's stop button aborts a hung turn, and the transcript shows a pending indicator for the whole wait), so this is "no error explaining the hang," not "stuck forever."
- [ ] **LocalCode: Ollama model catalog doesn't hot-reload** — `wigl-widgets/LocalCode/opencodeConfig.ts` syncs Ollama's installed models into `~/.config/opencode/opencode.jsonc` once, before `opencode serve` starts; editing that file while the server is already running has no effect until restart (verified live). A model pulled via `ollama pull` while the widget is already running won't appear until the server restarts, and nothing in the UI triggers that (`useOpencodeServer.ts`'s `restart()` exists but nothing calls it). Fix shape: poll Ollama's model list periodically, diff against what's already synced, call `restart()` when it changes.
- [ ] **LocalCode: extend the housekeeper model to a second consumer** — `wigl-widgets/LocalCode/housekeeper.ts`'s `runHousekeeperPrompt()` (a toolless, throwaway-session call against a small/fast local model, `config.ts`'s `DEFAULT_HOUSEKEEPER_MODEL`) is only ever called by `generateSessionTitle()` today. Trigger: a second concrete use shows up (summarizing a long transcript before compaction, naming a fork) — reuse `runHousekeeperPrompt()` for it rather than building a new call path. Must pass a toolless `agent` the same way `generateSessionTitle` does (`agent: "title"`) — Ollama 400s on a tool-incapable model given the default `"build"` agent's full tool schema.
- [ ] **LocalCode: one `opencode serve` per monitor, each with its own session list** — each monitor's `Desktop` is its own JS realm (see `docs/architecture.md`), so two monitors both running a LocalCode instance today spawn two independent `opencode serve` processes on two random ports, each with its own session list — no error, just silently disconnected state between them. Fine for the common single-monitor case. Fix shape: a lock file recording the chosen port (or a fixed port), so a second instance on another monitor discovers and reuses the first instance's server instead of spawning its own.
- [ ] **Cross-monitor drag col/row offset on screens of different sizes** — reported symptom: dragging a widget from a smaller screen to a bigger one (or vice versa) lands it at an unexpected position. A static read of `onPointerMove`'s foreign-monitor branch in [Desktop.tsx](src/wigl/Desktop.tsx) (target `col`/`row` come from `pxToCol`/`pxToRow` against the target monitor's own `colsForWidth`) didn't turn up an obvious cause on paper — `d.offX`/`d.offY`, `TILING.padding.top`, and the `cols`/clamp math all check out as monitor-size-aware statically, so this needs a live repro to pin down, not another static read. The one untested lead: `monitors.current` normalizes `availableMonitors()` rects by each monitor's own `scaleFactor` while `e.screenX`/`e.screenY` are taken as-is — if a platform reports `screenX`/`screenY` in a scale that isn't uniform across displays of different DPI, that mismatch would reproduce exactly this symptom. Needs a live multi-DPI multi-monitor rig to confirm. Fix shape once confirmed: a small helper that recomputes a relative `col`/`row` for monitor B from monitor A's `col`/`row` and each monitor's own column/row capacity, instead of reusing a raw pixel offset across monitors.
- [ ] **Windowed-mode interactive flows unverified end-to-end** — the Wayland/GNOME windowed flow (`docs/architecture.md`) builds and launches cleanly on a real Linux/GNOME machine (correct mode detection, clean log, page load), but drag/drop within the single window, `useStorage` read/write, the per-widget error boundary actually catching a crash, and the repos widget's Linux-specific shell paths (`wigl-widgets/repos/commands.ts`'s `xdg-open`/VS Code CLI/GitHub Desktop branches) haven't been exercised interactively — no input-synthesis tool was available in the environment this was last checked from. Trigger: someone with hands on a real Linux/GNOME machine spends 15–20 minutes actually dragging widgets, toggling repos-widget settings, and clicking its action buttons.
- [ ] **(Low priority) Drag ghosting/residue in windowed mode (GNOME/Wayland)** — dragging a widget leaves a visual trail of its previous position(s) that doesn't clear until something forces a repaint. Not reproduced interactively (no `ydotool`/`wtype`/`xdotool` available in the environment this was last investigated from), so this is a hypothesis: `.wigl-widget` (`src/App.css`) is `will-change: transform` with its position written via raw `el.style.transform` on every `pointermove` during a drag ([Desktop.tsx](src/wigl/Desktop.tsx)'s `onPointerMove`) — a GPU-layer-promoted transform animated at pointer rate is a known trigger for WebKitGTK compositor damage-region bugs, and `lib.rs`'s default `WEBKIT_DISABLE_DMABUF_RENDERER=1` on Linux (a workaround for a *different* bug) forces a fallback rendering path that's a plausible place for this one to show up. Cheap things to try first, in order: (1) `WEBKIT_DISABLE_DMABUF_RENDERER= bun run qa:app` (empty value overrides the default) — if ghosting disappears, the two workarounds are in tension and need a driver-specific condition instead of a blanket default; (2) `WEBKIT_DISABLE_COMPOSITING_MODE=1` as a second data point; (3) if neither clears it, check `journalctl --user -b 0 | grep -i webkit` for a Mesa/driver-level message while reproducing. Trigger: someone with a GNOME/Wayland machine and 20 minutes to run the two env-var A/B tests above.
- [ ] **Escape doesn't cancel a drag** — deliberate gap, not an oversight: `screen-*` windows are `alwaysOnBottom` and rarely become key, so a `keydown` listener isn't a reliable place to catch Escape today. Trigger: revisit if/when one of these windows does become key for another reason (e.g. a command palette), since that would give a reliable focus target to hang the listener off.
- [ ] **Slow iteration loop when editing a widget** — `bun run plugin:install` writes to the app-data dir, and nothing tells a running app to re-read it, so it's build → install → relaunch every time. `loadPlugins()` is already idempotent, so a watch mode plus a "reload plugins" global action would cut the loop to one keystroke. Trigger: someone finds the build→install→relaunch loop annoying enough to spend an afternoon on it.
- [ ] **Plugin storage keys aren't namespaced** — `useStorage`/`useQuery` write into one shared kv table keyed by whatever string the caller passes, so two plugins picking the same key silently share (and clobber) state, with nothing scoping a key to the plugin that owns it. Harmless with today's hand-installed plugins; a real bug the first time two independently-authored ones collide. Fix shape: have the registry hand each plugin a `useStorage` pre-bound to a `<plugin-id>:` prefix rather than the raw hook — the registry already builds a per-plugin view of `@/wigl/hooks`, so there's a natural place for it with no new concept.
- [ ] **The plugin registry chunk carries all of `lucide-react`** — `registry.ts` holds a live reference to every module it can serve, so the whole icon set lands in one chunk (~618kb unminified). It's dynamically imported and only paid once a plugin is actually installed, which is why this isn't urgent. Trigger: someone notices first-plugin-load latency. Fix shape: serve icons through a lazy per-icon lookup instead of a namespace import, which also removes the "host must ship every icon a plugin might want" coupling.
- [ ] **`useQuery`'s SQL cache never evicts** — `src/wigl/storage/useQuery.ts`'s `useSql: true` path writes `query_<key>` rows into the shared kv table but nothing ever deletes one, so a renamed or retired query key leaves a dead row behind forever (harmless, just clutter). Trigger: enough renamed/retired query keys to notice in the DB. Fix shape: none needed until then — a manual `DELETE FROM kv WHERE key LIKE 'query_%'` sweep is enough when it does.

## Features

- [ ] **A shared "widget is broken" error surface** — today the only on-screen explanation for something actually broken (a backing process failed to start, a request errored, a dependency isn't reachable) is whatever ad-hoc per-widget banner that widget happens to have — nothing shared, nothing that distinguishes "known, explainable state" (e.g. Ollama isn't running) from "an unexpected crash." Build a real `wigl` component — belongs in `src/wigl/` behind the `@/wigl` barrel per `docs/widgets.md`'s sharing rule, not owned by one widget — an error overlay/screen a widget can show when it has a real, current error condition, with room for a distinct styled treatment for a recognized cause vs. a generic failure. `wigl-widgets/LocalCode/useOpencodeServer.ts`'s `status`/`restart` and `client.sendPrompt`'s rejection path are a concrete first consumer to build it against.
- [ ] **LocalCode: branching instead of only revert-and-resend** — editing/resending a message today reverts the session to that point (opencode's `/session/{id}/revert`, undoing everything after it) and resends — there's no way to keep the original answer and explore an alternative alongside it. opencode's `/session/{id}/fork` endpoint exists in `wigl-widgets/LocalCode/client.ts`'s reach but nothing calls it. Building this means wiring `fork`, then a UI for switching between/viewing sibling branches of a session.
- [ ] **LocalCode: sub-agent visibility beyond the inline badge** — `PartRenderer.tsx` renders a spawned sub-agent as one inline one-line badge; opencode's `/session/{id}/children` endpoint (child sessions spawned by the current one) is in `client.ts`'s reach but nothing calls it. A real version would show children as nested/linked sessions in the sidebar, not just an inline marker in the transcript.
- [ ] **LocalCode: Ollama start/stop control** — `wigl-widgets/LocalCode/ollama.ts` only polls `GET /api/tags` for status; nothing spawns `ollama serve`. Explicit prior scoping call: Ollama is normally already running as a system service, so this was judged lower priority than opencode's own lifecycle. Revisit if that assumption stops holding (e.g. wigl is used somewhere Ollama isn't auto-started).
- [ ] **Widget resize** — today `w`/`h` are a first-launch hint only; there's no interactive way to change a widget's grid size after it's placed. The drag grip was deliberately narrowed to the header's top-right corner (`WidgetHeader` in `src/wigl/widget.tsx`, `data-drag-handle`) specifically so a resize handle has an uncontested spot to live — the natural pairing is a `data-resize-handle` grip at the bottom-right corner of `<Widget>`'s root, driving `reportGrid`'s `w`/`h` through the same `reflow`/`settle` machinery `src/wigl/Desktop.tsx` already uses for drag. Trigger: someone wants to actually resize a widget, not just reposition it.
- [ ] **Multiple instances of one widget type** — today a widget is exactly one folder = one id = one instance, so e.g. two clocks on different timezones is impossible. `<Widget w h col row>` itself doesn't care about identity; the gap is discovery (folder name *is* the id) and storage (each instance needs its own key, not a shared one). A plugin's `package.json` (`wigl` key) is the natural place for this to land — a plugin declaring it's instantiable, with the user's chosen instances and per-instance overrides stored like any other layout state. Trigger: a concrete want for two instances of one widget type.
- [ ] **A plugin is not sandboxed** — `src/wigl/plugins/registry.ts` controls which modules a plugin can import, which is real (it's how a withheld permission actually withholds something), but plugin code runs in the host's JS realm with `csp: null`, so `window.__TAURI_INTERNALS__` is reachable directly by anything that wants it. Acceptable today because plugins are hand-installed from a local folder by the person running the app; stops being acceptable the moment plugins are installed from a URL or a registry. Fix shape when that trigger arrives: run each plugin in a worker or sandboxed iframe with the host API exposed over a message port, or adopt Tauri's isolation pattern — both large enough to want their own design pass, and cheaper to adopt before a plugin ecosystem exists than after.
- [ ] **(Very low priority) GNOME-native overlay flow via a Shell extension** — Wayland/GNOME sessions get the windowed flow (`docs/architecture.md`) instead of the real desktop-overlay one, because stock GNOME Wayland refuses a client absolute positioning and always-below/always-on-top stacking (click-through itself works fine over Wayland; it just isn't useful without one of those two). A GNOME Shell extension ([desktop-widgets](https://github.com/NiffirgkcaJ/desktop-widgets)-style) could plausibly grant enough positioning/stacking control to run the real per-monitor overlay flow under GNOME too. Not worth pursuing casually: it's an extra install step for the user, version-fragile against GNOME Shell updates in a way the current windowed flow isn't, and would need real QA on the positioning/stacking contract before switching GNOME users onto it by default. Trigger: someone actually bothered enough by the windowed flow's remaining UX gap (window doesn't stay pinned below/above other apps, doesn't span monitors) to want to try it.
