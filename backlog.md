# Backlog

Atomic tasks, not a priority-ordered roadmap. Each entry is a problem or gap
someone (or an agent) could pick up and finish in one sitting without asking
"what does this mean?" first. Product ideas live in `docs/future-ideas.md`;
this file is defects, gaps, and known ceilings in what already exists.
Code-organization/quality heuristics (file size, naming, future-proofing)
live in `docs/principles.md`, not here — that's a standing rule to apply
continuously, not an atomic task to finish once.

Two sections, by size of change, not urgency — there's no priority order
within or across them. Items are numbered per section (`B1`, `F1`, ...) so
they can be referenced elsewhere; numbers aren't stable across edits — if
you need to point at one from another doc, quote its title, not just the
number.

- **Bugs** — existing functionality doesn't do what it's supposed to, or a
  targeted, self-contained fix/tweak to something that already works.
- **Features** — a capability that doesn't exist today, big enough that
  building it changes the current flow rather than just patching it.

Rules for keeping this file real:

- Every entry must be actionable right now. If it's not, it doesn't belong here.
- One clear next step per entry, not a menu of options — if a decision only the
  owner can make is genuinely blocking, say so in one line and name the default
  to fall back on, don't leave it open-ended.
- When an item is fixed, delete it. Don't check it off and leave it, don't move it to a "done" or "changelog" list — git history is the changelog.
- When a decision is made and closed with no remaining follow-up work, delete it too. Don't keep a "Decided / won't fix" graveyard.
- No dates, no "as of this session", no "swept on", no references to when something was added or by whom. This file describes the current state of the codebase, not its history.
- If a fix is genuinely speculative (no concrete trigger yet), say so plainly and give the trigger condition — don't leave vague "might be nice" entries.
- Prefer deleting or rewriting a stale entry over leaving it half-true when the code has moved past it. New entries follow this same file's own rules — keep it that way.

## Bugs

- [ ] **B8 — Cross-monitor drag col/row offset on screens of different sizes.** Reported symptom: dragging a widget from a smaller screen to a bigger one (or vice versa) lands it at an unexpected position. A static read of `onPointerMove`'s foreign-monitor branch in [Desktop.tsx](src/wigl/Desktop.tsx) didn't turn up an obvious cause — needs a live repro, not another static read. One untested lead: `monitors.current` normalizes `availableMonitors()` rects by each monitor's own `scaleFactor` while `e.screenX`/`e.screenY` are taken as-is — if a platform reports screen coordinates in a scale that isn't uniform across displays of different DPI, that reproduces exactly this symptom. Fix shape once confirmed: recompute a relative `col`/`row` for the target monitor from the source monitor's `col`/`row` and each monitor's own column/row capacity, instead of reusing a raw pixel offset across monitors.
- [ ] **B11 — Escape doesn't cancel a drag.** Deliberate gap: `screen-*` windows are `alwaysOnBottom` and rarely become key, so a `keydown` listener isn't reliably reachable today. Revisit only if/when one of these windows does become key for another reason (e.g. a command palette), since that would give a reliable focus target to hang the listener off.
- [ ] **B15 — LocalCode: Ollama models get no explicit context window, so opencode/Ollama fall back to a small default.** `opencodeConfig.ts`'s `syncOllamaModels` writes each model's `opencode.jsonc` entry with just `{ name, variants? }` — no `limit.context`/`limit.output`, and no `options.num_ctx` on the provider block. Verified live: `ollama show <model>` reports no `num_ctx` override for any locally pulled model, so Ollama runs its own built-in default context (small — a few thousand tokens), which agentic tool-call transcripts blow through fast. Fix shape: add a `num_ctx` (provider-level `options`, applies to every request against that Ollama instance — Ollama's OpenAI-compatible endpoint reads it per-request) and per-model `limit.context`/`limit.output` in `syncOllamaModels`'s written config, sized to what the owner's hardware can actually hold in VRAM/RAM at the chosen quantization — this is a real memory/latency tradeoff (bigger context = slower + more RAM), not a one-size-fits-all default, so it needs an owner-set value (e.g. a widget setting) rather than a silently-picked number.
- [ ] **B16 — LocalCode: opencode injects the project's AGENTS.md/CLAUDE.md into every agent's system prompt, regardless of tool permissions.** Verified live: even `wigl-chat` (the toolless default agent, `opencodeConfig.ts`'s `syncChatAgent`) rambles about wigl's own architecture on an unrelated prompt — `permission: "deny"` only gates tool access, not this. There's no confirmed per-agent opencode config for "keep the default system prompt, drop the project-file injection" — `AgentConfig`'s `prompt` field replaces the whole system prompt outright (riskier, unverified what else that loses). Trigger: confirm live whether `prompt` can *append/override just the instructions section* rather than the whole thing (check opencode's source for how `prompt` composes with its built-in default), then decide whether that's worth wiring into `syncChatAgent`.
- [ ] **B17 — LocalCode: killing wigl orphans its child `opencode serve` process instead of stopping it.** `useOpencodeServer.ts`'s cleanup (`handleRef.current?.stop()`) only runs when React unmounts the widget — it never fires when the whole app is killed (`pkill -x wigl`/`scripts/kill.sh`/`verify.sh`'s "kill any stale instance" step, which only matches the `wigl` process name, not its children). Verified live: after several `bun run verify` relaunches, multiple `opencode serve` processes were still running, each bound to its own random port and holding whatever config it booted with — invisible to the running widget (it always talks to the port its own launch returned) but a real leaked-process/stale-config trap for anyone probing a port by hand, and wasted resources over a long dev session. Fix shape: either track the spawned child's PID on the Rust side and kill it when the `wigl` process exits (a `RunEvent::Exit` handler in `src-tauri/src/lib.rs`), or have `scripts/kill.sh`/`verify.sh` also `pkill -f "opencode serve"` before relaunching.
- [ ] **B18 — LocalCode: opencode may run its own native session-title agent in parallel with the widget's own housekeeper.** Noticed live in a debug `opencode serve --print-logs` trace: an `agent=title` stream fired on a session's first message *before* wigl's own `housekeeper.ts` had made any request against it. If opencode has built-in automatic titling independent of `generateSessionTitle`, the two could be racing to set the same session's title (or opencode's own native title could be what actually shows up while the housekeeper's request is redundant, wasted local-model work). Trigger: confirm live whether `POST /session` or the first `POST /session/{id}/message` triggers an opencode-native title generation regardless of any client-side call, and if so decide whether `housekeeper.ts`'s title generation is still needed at all or should just read whatever title opencode already produced.
- [ ] **B14 — The plugin registry chunk carries all of `lucide-react`.** `registry.ts` holds a live reference to every module it can serve, so the whole icon set lands in one chunk (~618kb unminified). It's dynamically imported and only paid once a widget is actually installed, which is why this isn't urgent. Trigger: someone notices first-widget-load latency. Fix: serve icons through a lazy per-icon lookup instead of a namespace import, which also removes the "host must ship every icon a widget might want" coupling.

## Features

- [ ] **F2 — LocalCode: branching instead of only revert-and-resend.** Editing/resending a message today reverts the session to that point (opencode's `/session/{id}/revert`, undoing everything after it) and resends — no way to keep the original answer and explore an alternative alongside it. opencode's `/session/{id}/fork` endpoint is already in `wigl-widgets/LocalCode/client.ts`'s reach but nothing calls it. Wire `fork`, then build a UI for switching between/viewing sibling branches of a session.
- [ ] **F3 — LocalCode: sub-agent visibility beyond the inline badge.** `PartRenderer.tsx` renders a spawned sub-agent as one inline one-line badge; opencode's `/session/{id}/children` endpoint (child sessions spawned by the current one) is in `client.ts`'s reach but nothing calls it. A real version would show children as nested/linked sessions in the sidebar, not just an inline marker in the transcript.
- [ ] **F4 — LocalCode: Ollama start/stop control.** `wigl-widgets/LocalCode/ollama.ts` only polls `GET /api/tags` for status; nothing spawns `ollama serve`. Scoped out before: Ollama is normally already running as a system service, so this was lower priority than opencode's own lifecycle. Revisit if that assumption stops holding (e.g. wigl used somewhere Ollama isn't auto-started).
- [ ] **F5 — Widget resize.** Today `w`/`h` are a first-launch hint only; no interactive way to resize a widget after it's placed. The drag grip was deliberately narrowed to the header's top-right corner (`WidgetHeader`, `data-drag-handle`) specifically so a resize handle has an uncontested spot to live — the natural pairing is a `data-resize-handle` grip at the bottom-right corner of `<Widget>`'s root, driving `reportGrid`'s `w`/`h` through the same `reflow`/`settle` machinery `Desktop.tsx` already uses for drag. Trigger: someone actually wants to resize a widget, not just reposition it.
- [ ] **F6 — Multiple instances of one widget type.** Today a widget is exactly one folder = one id = one instance, so e.g. two clocks on different timezones is impossible. `<Widget w h col row>` itself doesn't care about identity; the gap is discovery (folder name *is* the id) and storage (each instance needs its own key, not a shared one). A widget's `package.json` (`wigl` key) is the natural place for this to land — declaring itself instantiable, with the user's chosen instances and per-instance overrides stored like any other layout state. Trigger: a concrete want for two instances of one widget type.
- [ ] **F7 — (Very low priority) GNOME-native overlay flow via a Shell extension.** Wayland/GNOME sessions get the windowed flow instead of the real desktop-overlay one, because stock GNOME Wayland refuses a client absolute positioning and always-below/always-on-top stacking. A GNOME Shell extension ([desktop-widgets](https://github.com/NiffirgkcaJ/desktop-widgets)-style) could plausibly grant enough positioning/stacking control to run the real per-monitor overlay flow under GNOME too. Not worth pursuing casually — extra install step, version-fragile against GNOME Shell updates, needs real QA on positioning/stacking before switching GNOME users onto it by default. Trigger: someone actually bothered enough by the windowed flow's remaining UX gap (window doesn't stay pinned below/above other apps, doesn't span monitors) to try it.
- [ ] **F8 — Double-click-to-resize as an alternative entry point to F5.** Once F5's resize handle exists, add a second way in: double-clicking the resize grip switches the grid from drag mode to a dedicated resize mode for that widget (rather than requiring a click-drag on the grip itself), so resize and reposition read as two distinct gestures instead of one overloaded drag. Depends on F5 landing first — this is a UX refinement on top of it, not a standalone feature. Trigger: after F5 ships, if plain click-drag-to-resize on the grip turns out to feel error-prone or ambiguous with dragging.
- [ ] **F9 — Pinboard mode: free placement, no auto-stacking.** An alternate grid mode where dragged widgets can overlap freely and never get pushed/reflowed by `reflow`/`settle` (`src/wigl/grid/math.ts`) — pure user-controlled position, like a corkboard. Needs: (1) a per-monitor or per-widget toggle between today's collision-avoiding grid and this mode, (2) since overlap is now legal, a z-order story — simplest version is "the currently-selected/dragged widget gets a higher z-index than everything else, no full stacking history needed," only build the fuller N/N-1/N-2 rotating stack if the simple version proves insufficient in practice. Trigger: a concrete want for overlapping widgets, not just a nice-to-have — this is a bigger flow change than a patch, matches this file's "Features" bar.
