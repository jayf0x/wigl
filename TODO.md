## Linux

- [ ] Windowed-mode interactive flows unverified end-to-end. The Wayland/GNOME windowed flow builds and launches cleanly on a real machine (correct mode detection, clean log, page load), but drag/drop within the single window, `useStorage` read/write, the per-widget error boundary actually catching a crash, and the repos widget's Linux-specific shell paths (`xdg-open`/VS Code CLI/GitHub Desktop branches) haven't been exercised interactively. Trigger: someone with hands on a real Linux/GNOME machine spends 15–20 minutes dragging widgets, toggling repos-widget settings, and clicking its action buttons.
- [ ] (Low priority) Drag ghosting/residue in windowed mode (GNOME/Wayland). Dragging a widget leaves a visual trail of its previous position(s) that doesn't clear until something forces a repaint. Not reproduced interactively yet — hypothesis: `.wigl-widget`'s `will-change: transform` position, written via raw `el.style.transform` on every `pointermove`, is a known trigger for WebKitGTK compositor damage-region bugs, possibly interacting with `lib.rs`'s default `WEBKIT_DISABLE_DMABUF_RENDERER=1`. Cheap A/B tests, in order, on a GNOME/Wayland machine: (1) `WEBKIT_DISABLE_DMABUF_RENDERER= bun run qa:app` (empty value overrides the default), (2) `WEBKIT_DISABLE_COMPOSITING_MODE=1`, (3) `journalctl --user -b 0 | grep -i webkit` for a driver-level message while reproducing.
